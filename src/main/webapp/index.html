Default settings for new rooms (by name pattern)

When a room is created, the rule matching its name is applied automatically. * matches any text and ? one character; the most specific rule wins.

How rules work

Patterns use shell-style globs (e.g. *_ext matches mychat_ext; * matches every room). When several rules match a name the most specific one wins (most literal characters), so * acts as a catch-all. A non-federated rule excludes a name pattern from a broader rule. Auto-map requests a same-named room link on each visible peer; combined with the peer's auto-accept, two servers using the same naming rule auto-link with no clicks.

Local groups — share with other servers

Open a group (▸) and tick the servers that should get its members as contacts. The other server's admin decides which of their users see them.

How sharing works

Like Openfire's Contact List Sharing, across servers. Each server receives one contact list: the members of every group shared with it, kept in step with group membership. Their users see the presence and avatar of the contacts you share. Your users don't see theirs unless that server shares back. A server behind an untrusted link is listed only when that link allows contact lists (the untrusted peer's settings panel on the Peers tab).

Contact lists received from other servers

Open a server's list to put its contacts in your users' contact lists, make them searchable in the federated directory, or both.

Mapping, Deny and Delete

Map a server's list to one or more local groups (or all users). The plugin keeps an Openfire shared group, federation-contacts-<server>, holding those contacts, which puts them in each chosen user's contact list under the roster group name you pick. If the server stops sharing someone, they're removed. Removing the mapping deletes the group, which takes the contacts out of every contact list. Instead of or as well as that, tick Searchable in the federated directory: your users can then look the contacts up and add the ones they want, and nothing is put in anyone's contact list. Deny keeps a server's entry but drops every list it sends and stops using its contacts until you allow it again. Delete removes the entry, for a server that stopped sharing or no longer exists; if it shares again, its list shows up as a new one.

The Openfire group provider is read-only (for example LDAP), so the plugin cannot create groups for received lists.

What the directory is

A user search service (XEP-0055) over the received lists you make searchable on Contact sharing. Your users find it in their client's user search or service discovery, look people up on other servers, and add or message the ones they want. Only this server's users can search it. It runs while at least one list is searchable.

Searches from other servers

User searches from other servers are refused unless their server is ticked here. Your own users' searches are not affected.

Why they are refused

Openfire's Search plugin answers anyone with every user on this server, whatever you share, and other search services may do the same. So the federation plugin refuses user searches from other servers' users, over native S2S or the overlay, unless their server is ticked here. A server that tried is listed with how many searches were refused.

Relay
Federate file shares (HTTP File Upload)
A shared file is copied to the servers whose users receive the message, and each client downloads it from its own server.
Details
When enabled (default), a file shared via HTTP File Upload is relayed over the federation to exactly the servers whose users receive the message (mapped-room peers, a 1:1 recipient's home — never broadcast), re-hosted there, and the link is rewritten so every client downloads from its own server. Local-only traffic never leaves; transit hops never store a copy.

ClamAV
Virus scan federated files (ClamAV)
Files are scanned before they leave this server and again before a local user can download one. If the scanner cannot be reached, the file is not relayed.
Details
When enabled, a file's content is scanned by a clamd daemon at both ends of a relay: here on upload, before the file is offered to any peer, and again on the receiving server before it becomes servable to a local recipient. A pure transit hop never scans, because it never decodes content. A scan that cannot complete (clamd unreachable) is treated as a failure at either end: the relay fails closed rather than moving unscanned content while this is on.

What gets a file rejected
Any gate can block a file: the allowed-extensions list (egress, before it's ever offered to a peer, or ingress as defense in depth), the content-vs- extension sniff check, a SHA-256 mismatch, or the virus scanner. A file rejected here never reaches the virus scan (extension/content checks run first). Allow users to reach remote rooms across federation
Users on other servers can join local rooms directly, even rooms that are not mapped. Turn off to make rooms reachable only through a mapping.
Details
When enabled (default), a user on another server may traverse the federation network to join or post to a local MUC room directly over S2S, even when no federation mapping exists — so ad-hoc and private rooms that are never advertised stay reachable. Federation's own traffic is unaffected. Disable to lock rooms down so they are only reachable through an explicit federation mapping.

Messages & presence
Relay 1:1 messages over federation
Private messages to users on reachable servers travel hop by hop through the federation, so they work where there is no direct S2S link.
Details
When enabled, a private message a local user sends to a user on an overlay-reachable peer is relayed hop-by-hop through federation (so it works even across untrusted edges with no direct S2S). Replies route back the same way. Disable to use Openfire's native S2S for 1:1 chat.

Makes a newly added contact on a multi-hop server show as online. Recommended on.
Details
When a local user adds a contact on a multi-hop peer, Openfire's own presence probe leaks to native S2S and fails (no direct link), so the contact never shows online. With this on, the probe is re-issued over the federation overlay so the contact's presence is pulled.

Connection timers
S2S keepalive interval
How often each reachable peer is pinged so Openfire does not close an idle link. Minimum: 30 s. Default: 240 s.
Details
Sends a lightweight ping to each reachable peer at this interval to prevent Openfire from closing idle S2S sessions. Must be less than Openfire's xmpp.server.idle setting (milliseconds ÷ 1000 × 0.8). The default is safe for Openfire's built-in 6-minute idle timeout.
s
Max reconnect interval (back-off cap)
Longest wait between attempts to reconnect an unreachable peer. Minimum: 5 s. Default: 30 s.
Details
Retries use exponential back-off starting at 5 s: 5 s → 10 s → 20 s → … capped at this value. On reconnect the back-off resets automatically.
s
Mapping probe interval (mapping-ping)
How often each room mapping is tested end to end. 0 turns the probe off. Minimum: 15 s. Default: 30 s.
Details
Probes every active room mapping end-to-end at this interval; the mapped domain answers with a pong routed back across the overlay. Three unanswered probes in a row flag the mapping as ⚠ not responding and evict its remote occupants (≈2 minutes at the default cadence). Applies immediately — no restart needed.

# The federation overlay protocol

This directory is a **wire specification**. Everything else in `docs/` explains how the Openfire plugin
is built; these documents describe only what travels between two servers, so that a server that is not
Openfire — Prosody, ejabberd, Tigase, Snikket, or something written from scratch — can implement a
module that federates with this one.

Nothing here requires Openfire. The protocol rides on ordinary server-to-server XMPP (RFC 6120 §4–5)
and uses only `<iq/>` stanzas in one namespace.

## Conventions

**Requirement keywords** — MUST, MUST NOT, SHOULD, MAY are used as in
[RFC 2119](https://datatracker.ietf.org/doc/html/rfc2119). "MUST" here means: an implementation that
does otherwise will be dropped, blocked, or will silently fail to interoperate with this one.

**Example domains** — `alpha.example`, `beta.example`, `gamma.example` are federating servers.
`conference.alpha.example` is a MUC service on `alpha.example`. Real deployments use whatever the
server's XMPP domain is; the protocol never assumes any relationship between a server's domain and
its MUC service domain except where explicitly stated.

**Examples are indented for readability.** Whitespace between elements is insignificant. Stanza `id`
attributes are shown as `f1`, `f2`, … — they are ordinary IQ ids, generated by the sender however it
likes, and the protocol never correlates on them (see [01-transport.md](01-transport.md#acknowledgement)).

**"This implementation"** means the Openfire plugin in this repository. Where its behaviour is a
choice rather than a protocol requirement, that is called out — you are free to make a different
choice as long as the wire contract holds.

## What this protocol is for

Plain XMPP S2S already federates. This overlay exists to add four things it does not give you:

1. **Multi-hop reachability.** Two servers with no direct link, no mutual DNS, or no mutual TLS trust
   can still exchange traffic through a common neighbour. The overlay carries its own distance-vector
   routing table and forwards stanzas hop by hop.
2. **Room joining.** Two MUC rooms on different servers can be *mapped* so that occupants of each
   appear in the other, without either side's users having to join a foreign room.
3. **Administrative consent.** Every room, every mapping and every route is opt-in on both sides, with
   an explicit accept/reject handshake and per-peer exposure controls.
4. **Content relay.** File uploads, vCards, avatars and PEP items follow the same path, so a client on
   the far side of three hops downloads from *its own* server.

If you only need one-hop federation between two servers that can already reach each other, you do not
need this protocol.

## Scope and non-goals

- **No end-to-end authentication.** The overlay trusts hop-by-hop, exactly as S2S does. A relaying
  server can read and modify anything it carries. Stanzas are not signed. This is a deliberate
  trade-off and it shapes several of the rules in [09-validation.md](09-validation.md); design your
  deployment's trust topology accordingly.
- **No transport of its own.** The overlay assumes a working S2S link between adjacent peers, with
  whatever authentication (dialback, TLS + SASL EXTERNAL) the two servers negotiated. Bringing that
  link up is out of scope.
- **No versioning of individual actions.** Compatibility is by attribute: unknown attributes are
  ignored, absent attributes fall back to a documented default. There is no capability negotiation
  beyond the `<version/>` in `peer-announce`, which this implementation does not yet act on. See
  [10-conformance.md](10-conformance.md#version-compatibility).
